Crucible

A real-time security system that watches a vehicle’s internal network for unusual activity and possible attacks.

Personal project · November 2025 to present
Initial build completed January 2026

View the code ↗

Why I built it

Modern vehicles constantly exchange data about steering, speed, braking, and other controls. If someone sends a fake message into that network, the vehicle needs to detect it quickly enough to respond.

I built Crucible to explore how machine learning could catch those attacks directly on hardware inside the vehicle. It works with comma.ai’s openpilot platform and Panda OBD-II interface, watching live CAN bus data for packet spoofing, unusual steering commands, and attempts to take control of the vehicle.

How it works

Crucible monitors 11 vehicle signals at once. It reads them in short windows of 50 time steps, which gives the model enough context to notice when the vehicle’s behaviour suddenly changes.

The detection model is a Temporal Convolutional Network built for time-series data. It compares incoming telemetry with the patterns it learned from normal driving. If the error moves too far from the baseline MSE of 0.3101, the system treats the activity as suspicious.

Each prediction takes less than 15 milliseconds on edge hardware. I used TorchScript and Core ML with FP16 precision to keep inference fast enough to run inside the vehicle without relying on a remote server.

Building the test environment

Testing this safely required a simulated vehicle.

CARLA runs on macOS and handles the driving simulation. A Linux container runs ROS, receives the live telemetry, and passes it to the detection model over a virtual network connection.

I also built a dashboard with three risk levels. As the telemetry becomes more unusual, the dashboard raises the alert level so the system can respond based on the severity of the event.

Testing attacks

Normal driving data was only part of the test. I needed to see what happened when the incoming data was deliberately wrong.

I built a fault-injection suite that sends hostile CAN packets, changes packet timing, and inserts fake steering commands. This exposed cases where the model performed well on familiar data but struggled when an attack changed the shape or timing of the signals.

Those tests helped me tune the alert thresholds and check how the full pipeline behaved under pressure.

What I learned

Getting the model below 15 milliseconds was useful, but inference speed was only one part of the latency budget. Memory allocation, thread scheduling, telemetry delivery, and alert handling could still slow the system down.

Crucible taught me to measure the entire path from incoming signal to visible alert. It also made fault injection a normal part of my testing process, especially for systems that may eventually interact with real hardware.
